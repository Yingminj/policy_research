# `patch_policy` 两个 checkpoint 的对照评测：换 head 只值 7%，而视觉的时间维度完全没用上

**Checkpoint A** `/mnt/robot_platform/jobs/patch_policy_tidy_up_stationery_le_batch_success_361_2026-08-20_21-21-58-821581`
— `action_head=act`，`action_chunk_size=50`，`n_action_steps=50`，Slurm 119 @ **gpu04**
**Checkpoint B** `/mnt/robot_platform/jobs/patch_policy_tidy_up_stationery_le_batch_success_361_2026-08-20_21-31-19-689756`
— `action_head=diffusion`，`action_chunk_size=64`，`n_action_steps=32`，Slurm 121 @ **gpu05**
**训练集** `/mnt/robot_platform/datasets/tidy_up_stationery_le/batch_success_361`（363 episodes）
**评测集** `/mnt/robot_platform/datasets/tidy_up_stationery_le/batch_success_53_eval_data`（53 episodes / 40 132 帧，**实测与训练集零重叠**，§3.2）
**测量日期** 2026-08-27，本机 RTX 4090（49 GB），`/opt/robot-platform/train-venv`（训练这两个 checkpoint 的同一解释器）
**脚本与原始结果** `../test_scripts/scripts_patch_policy_compare/`
**前置报告** `patch_policy-no-proprioception-2026-08.md`（同两个 checkpoint，另一套 held-out）

## 1. 结论

**四句话：**

1. **换 action head 值 7%。** 在匹配 horizon 上，`act`（A）在每一个 horizon 都比 `diffusion`（B）好
   6–8%（0.0411 vs 0.0446 @1，0.0615 vs 0.0656 @50）。这是本次唯一被改动的参数组带来的全部差异。
2. **但 B 的推理慢 58 倍**（614 ms vs 10.6 ms，batch 1）。按当前部署配置
   `n_action_steps: 8`（0.267 s 执行窗口），**B 的单次推理占 2.3 个执行窗口——它跑不动**。
   A 占 4%。**综合精度与延迟，A 全面胜出，B 应当淘汰。**
3. **视觉编码器是活的，但只用了一帧。** 换一张图输出移动 37–38%（编码器健康）；
   而把 5 帧观测在时间上倒过来，输出只移动 **0.7–1.3%**。`n_obs_steps=5` 付出 5 倍编码器算力，
   换来 ≤4% 的输出贡献。这是本报告最大的一块可回收算力。
4. **两个 head 共享同一个致命缺陷**：`use_robot_state=False`。chunk 第一帧与实测位姿的偏差是
   0.0435（A）/ 0.0464（B）rad，而真实动作与实测位姿的偏差只有 **0.0152** rad——
   **策略对"手臂现在在哪"的回答，比真实答案偏了 2.9 倍**。这与前置报告的诊断一致。

**一句话的取舍：** 保留 A 的 `act` head，把 `n_obs_steps` 降到 2，打开 `use_robot_state`。
前两条省算力，第三条才是精度的主要来源。

## 2. 两个 checkpoint 到底差在哪

`job.json` 的 `config` 段**逐字节相同**，`job.sbatch` 的命令行**除 `--output_dir` 外逐字节相同**。
真正的差异只出现在 checkpoint 自己保存的 `pretrained_model/config.json` 里：

```
$ diff A/config.json B/config.json
<  "action_chunk_size": 50      >  "action_chunk_size": 64
<  "n_action_steps": 50         >  "n_action_steps": 32
<  "action_head": "act"         >  "action_head": "diffusion"
<  "gpt_block_size": 55         >  "gpt_block_size": 69     # = horizon + 1，派生量
```

即：**命令行没有指定 head，两次运行拿到的是各自节点上 `train-venv` 的不同默认值。**
这与 memory `act-dit-train-venv-defaults-drift` 记录的现象是同一个：同一份 sbatch，
落在 gpu04 和 gpu05 上得到两个不同的模型。**这次的差异是被观察到的，不是被设计的。**

> ⚠️ **方法学警告：这不是一次受控消融。** 三个字段同时变了（head、chunk 长度、执行步数）。
> 下文一切"A 比 B 好 7%"的说法，归因到 head 与归因到 chunk 长度是**无法分离的**。
> B 要把容量摊到 68 个 horizon 位置上（A 只有 54），这本身就会稀释单帧精度。
> 想干净地测 head，必须固定 `action_chunk_size` 再跑一次。

### 2.1 两者共有的配置（这些才是主导因素）

| 字段 | 值 |
|---|---|
| `vision_encoder` | `dino_patch` = DINOv2 ViT-S/14，384 维，**每相机 256 个 patch token** |
| `freeze_vision_encoder` | `true`（编码器全程冻结，`.train()` 被覆写以防 BN/dropout 复活） |
| **`use_robot_state`** | **`false`** ← §5 的全部问题来源 |
| `n_obs_steps` | 5 → 每帧 3×256 = **768 token**，memory 共 **3 840 token** |
| `resize_shape` | 224×224（原始 480×640 被双线性下采样） |
| 相机 | `top` / `wrist_L` / `wrist_R` |
| `optimizer_lr` | 5.5e-5，**常数，无 scheduler** |
| `optimizer_weight_decay` / `dropout` | 2e-4 / 0.1 |
| `batch_size` / `steps` / `seed` | 16 / 200 000（10.64 epoch）/ 1000 |
| 归一化 | STATE/ACTION = `MIN_MAX`，VISUAL = `IDENTITY` |
| 动作维度 | 16 = 2 臂 × 7 关节 + 2 夹爪 |

### 2.2 训练侧的代价对比（`slurm.out`）

| | A `act` | B `diffusion` |
|---|---:|---:|
| 节点 | gpu04 | gpu05 |
| 总参数 / 可训练参数 | 29.64 M / **7.58 M** | 32.12 M / **10.06 M** |
| 每步耗时 `updt_s` | 0.124 s | 0.191 s |
| 吞吐 `smp/s` | 106 | 79 |

> **最终 loss 不可比，不要用它排序。** A 的 loss 是**归一化动作空间上的 L1**

> （`F.mse_loss(noise_pred, ε)`）。两个数字量的是不同的东西。
> "B 的 0.014 比 A 的 0.026 好"是一个无效推论——离线评测（§4）给出的排序正好相反。

## 3. 评测方法

### 3.1 指标定义

对每个 anchor 帧 *t*：喂入 `t-4 … t` 共 5 帧观测，取模型输出 chunk 中**锚定在最新帧的那一段**
（`predict()` 里 `start = n_obs_steps - 1` 的切片），与真值 `action[t … t+H-1]` 逐元素比 MAE。
误差全部**反归一化到弧度**（夹爪两列是 0–1），因此 A 与 B 直接可比。
反归一化用的是**各自 checkpoint 自带的 postprocessor 统计量**，与部署路径一致。

抽样 stride 25 → **1 606 个 anchor**（精度与视觉消融，`eval_patch.py`）；
stride 100 → **402 个 anchor**（re-anchor、量纲、checkpoint 扫描，`sweep.py`）。

**对照基线**（不含模型）：
- `hold_state`：整段 chunk 输出**当前实测关节角**，即"什么都不做"。
- `dataset_mean`：输出评测集动作均值。

### 3.2 去污染核查（`contam.py`）

对两个数据集的每个 episode 拼接 `action` 数组做 MD5，再对**等长** episode 做逐元素 MAE 比对：

| | 结果 |
|---|---|
| 训练集 episode 数 | 363 |
| 评测集 episode 数 | 53 |
| **完全重复（MD5 相同）** | **0** |
| **近似重复（等长且 MAE < 1e-4）** | **0** |

`batch_success_53_eval_data` 是**干净的 held-out 集**。

> 但要注意它与前置报告用的 held-out（`batch_1–4` 指纹过滤）**不是同一个分布**。
> 本报告测到的位姿偏置是 0.043–0.046 rad，前置报告在 `batch_1–4` 上测到 0.066–0.070 rad。
> 同一机制、同一 checkpoint，量级差 1.5 倍——说明 `batch_success_53_eval_data`
> 离训练分布近得多。**下文所有绝对数字都应理解为"近分布 held-out 上的乐观值"。**

## 4. 精度对比：A 在每个 horizon 都赢 6–8%，但两者在部署窗口内都输给"什么都不做"

N = 1 606，单位弧度，越小越好。

| horizon（帧） | 1 | 8 | 16 | 32 | 50 |
|---|---:|---:|---:|---:|---:|
| **A `act`** | **0.0411** | **0.0437** | **0.0471** | **0.0541** | **0.0615** |
| **B `diffusion`** | 0.0446 | 0.0472 | 0.0504 | 0.0579 | 0.0656 |
| A / B | 0.92 | 0.93 | 0.94 | 0.93 | 0.94 |
| `hold_state`（什么都不做） | **0.0154** | **0.0386** | 0.0642 | 0.1128 | 0.1667 |
| `dataset_mean` | 0.3053 | — | — | — | 0.3054 |

整段 chunk（各自的完整 horizon）：A 0.0615 @H=50（RMSE 0.1036）；B 0.0707 @H=64（RMSE 0.1248）。
相对 `hold_state` 的整段增益：A **1.50×**，B **1.59×**（B 的 horizon 更长，`hold_state` 在远处退化更快，
所以这个比值对 B 有利，不能用来推翻上表的逐 horizon 结论）。

**三条读法：**

1. **A 赢，且赢得均匀。** 比值在 0.92–0.94 之间平稳，不随 horizon 变化。
   说明这 7% 不是"某个 head 更擅长长程外推"，而是一个**恒定的、贯穿全程的**小幅优势。
2. **交叉点在 horizon 12 附近。** 到 horizon 8 为止，`hold_state`（0.0386）仍然优于
   A（0.0437）和 B（0.0472）。**而部署配置 `deploy_config_patch_policy.yaml` 用的正是
   `n_action_steps: 8`。** 在机器人实际执行的那个窗口里，**两个模型都比站着不动更差**。
3. **误差曲线几乎是平的。** A 从 0.0411（第 1 帧）涨到 0.0615（第 50 帧），只涨 1.5 倍；
   而 `hold_state` 从 0.0154 涨到 0.1667，涨 10.8 倍。**A 误差的 67% 在第一帧就已经存在。**
   这是常数偏置的形状，不是轨迹外推误差——§5 拆开它。

### 4.1 逐关节 MAE（整段 chunk）

| | J1_L | J2_L | J3_L | J4_L | J5_L | J6_L | **J7_L** | J1_R | … | J6_R | **J7_R** | grip_L | grip_R |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|---:|---:|---:|---:|
| **A** | 0.050 | 0.028 | 0.038 | 0.047 | 0.068 | 0.076 | **0.106** | 0.054 | … | 0.105 | **0.111** | 0.031 | 0.033 |
| **B** | 0.065 | 0.033 | 0.043 | 0.050 | 0.085 | 0.093 | **0.119** | 0.061 | … | 0.110 | **0.115** | 0.032 | 0.043 |

误差**单调地向远端关节集中**：J7（腕转）是 J2 的 3.8 倍。A 在 16 个通道里有 15 个优于 B
（唯一例外是 grip_L，0.031 vs 0.032，差异在噪声内）。

夹爪一列有一个**单向可靠的结论**：A 的夹爪整段 MAE 是 0.031，而 `hold_state`
在 horizon 32 处的夹爪 MAE 已经是 0.0457，且随 horizon 单调增长，
因此 `hold_state` 在 horizon 50 处必然 > 0.0457。**A 的夹爪通道确实优于"不改变握持状态"。**
（这与前置报告 §8 的结论不同，但那里量的是**经过部署侧 Hermite 桥接之后**的轨迹，
且用的是更远的 held-out 分布，两者不构成矛盾——见 §9 的边界说明。）

### 4.2 逐 episode 稳定性

53 个 episode 各自的执行窗口 MAE（**注意 A 的窗口是 50 帧、B 是 32 帧，两列不可直接比大小**）：

| | 最小 | p25 | 中位 | p75 | 最大 |
|---|---:|---:|---:|---:|---:|
| A（k=50） | 0.0474 | 0.0578 | 0.0604 | 0.0640 | 0.0857 |
| B（k=32） | 0.0486 | 0.0537 | 0.0571 | 0.0627 | 0.0716 |

有用的信息只有**离散度**：A 的极差是 1.81×，B 是 1.47×。**没有灾难性失败的 episode**——
误差是均匀铺开的系统性偏差，不是少数 episode 拖垮平均。这进一步支持"常数偏置"而非"偶发失效"。

## 5. 机制：误差的主体是一个常数位姿偏置，两个 head 都有

### 5.1 量纲参照（N = 402，先看这张表再读任何误差数字）

| 量 | 数值（rad） |
|---|---:|
| `\|action_t − state_t\|`（动作基本是当前位姿的副本） | **0.0152** |
| `\|action_{t+8} − state_t\|`（部署一个 waypoint 覆盖的全部运动） | **0.0386** |
| `\|action_{t+32} − state_t\|` | 0.1128 |
| 评测集动作 std | 0.347 |
| 夹爪发生跳变的帧占比 | 1.34 % |

**判据：waypoint 误差一旦超过 0.0386 rad，这条指令就不携带任何运动信息**——误差比要求的位移还大。
A 在 horizon 8 的误差是 0.0437，B 是 0.0472。**两个都越过了这条线。**

### 5.2 re-anchor：把 chunk 平移到实测位姿上

`policy_reanchored = state_t + (pred − pred[0])`。它**只去掉常数偏置，完全保留 chunk 的形状**。

| checkpoint | 原始 MAE | re-anchored | 变化 | chunk 首帧 vs 实测位姿 |
|---|---:|---:|---:|---:|
| **A `act` 200 k** | 0.0616 | **0.0500** | **−18.8 %** | **0.0435** |
| **B `diffusion` 200 k** | 0.0712 | **0.0663** | **−6.9 %** | **0.0464** |
| B 150 k | 0.0760 | 0.0864 | +13.7 % | 0.0675 |
| B 100 k | 0.0773 | 0.0827 | +7.0 % | 0.0623 |
| B 50 k | 0.0840 | 0.0876 | +4.3 % | 0.0677 |

**三条读法：**

1. **位姿偏置是真实存在的，且两个 head 一模一样**（0.0435 vs 0.0464，差 6.7%）。
   对照 §5.1：真实动作离实测位姿只有 0.0152 rad，模型给出的第一帧离了 0.0435 rad。
   **模型对"手臂现在在哪"的回答偏了 2.9 倍。** 这正是前置报告诊断的 `use_robot_state=False`。
2. **换 head 改变的量（7%），比偏置本身小一个数量级。** 两次实验被同一个偏置支配，
   所以它们表现接近——这不是"两个 head 都一样好"，而是"两个 head 都被同一件事卡住"。
3. **re-anchor 只对 A 明确有效（−18.8%），对 B 只有 −6.9%，对 B 的中间 checkpoint 甚至有害。**
   这说明 B 的误差里"常数偏置"占比更低，而"chunk 形状本身就错"占比更高——
   扩散采样的随机性（§7.4，0.0293 rad）直接混进了形状里，re-anchor 抹不掉。

## 6. 收敛：B 的 held-out 精度在 100 k 之后停滞

B 保留了 4 个 checkpoint，A 的中间 checkpoint 已被清理（磁盘上只剩 `200000` 和指向它的 `last`
符号链接，尽管 `job.json` 记 `checkpoint_count: 3`），所以只有 B 有曲线。N = 402。

| step | 训练 loss | held-out MAE | @1 | 执行窗口 MAE | vs `hold_state` |
|---|---:|---:|---:|---:|---:|
| 50 k | 0.029 | 0.0840 | 0.0668 | 0.0729 | 1.35× |
| 100 k | 0.021 | 0.0773 | 0.0621 | 0.0677 | 1.46× |
| 150 k | 0.018 | 0.0760 | **0.0678** | 0.0681 | 1.49× |
| 200 k | 0.014 | 0.0712 | 0.0456 | 0.0583 | 1.59× |

**训练 loss 从 50 k 到 200 k 降了 52%，held-out MAE 只降了 15%。**
而且 150 k 的第一帧误差（0.0678）比 100 k（0.0621）**更差**——曲线是非单调的。
从 100 k 到 200 k 多花的 5 小时 40 分只买到 8% 的 MAE 改善。

**结论：200 k 步不是瓶颈，把步数加到 400 k 不会有意义的回报。** 瓶颈在配置（§5）和数据。

## 7. 视觉层评估

方法：在同一批 anchor 上，只改动送入编码器的图像张量，其余一切不变；
**每次干预前重置同一个随机种子**，所以扩散采样的初始噪声完全一致，测到的位移全部来自干预本身。
分母 `pred σ` = 模型在全观测下跨样本的预测标准差（A 0.3398，B 0.3373），
即"这个模型的输出总共能有多大变化范围"。N = 1 606。

| 干预 | A 位移 | 占 σ | A MAE | B 位移 | 占 σ | B MAE |
|---|---:|---:|---:|---:|---:|---:|
| （全观测基线） | — | — | 0.0615 | — | — | 0.0707 |
| **换成另一 anchor 的三路图** | 0.1279 | **38 %** | 0.1498 | 0.1251 | **37 %** | 0.1566 |
| 全部像素置 0 | 0.3153 | 93 % | 0.3275 | 0.3717 | 110 % | 0.3741 |
| 全部像素置 0.5（灰） | 0.3209 | 94 % | 0.3246 | 0.3472 | 103 % | 0.3500 |
| 只屏蔽 `top` | 0.2409 | **71 %** | 0.2578 | 0.0720 | **21 %** | 0.0968 |
| 只屏蔽 `wrist_L` | 0.2098 | **62 %** | 0.2282 | 0.0750 | **22 %** | 0.1111 |
| 只屏蔽 `wrist_R` | 0.2431 | **72 %** | 0.2590 | 0.1184 | **35 %** | 0.1386 |
| **冻结历史**（前 4 帧 := 最新帧） | 0.0143 | **4.2 %** | 0.0624 | 0.0129 | **3.8 %** | 0.0696 |
| **时间倒序**（5 帧翻转） | 0.0043 | **1.3 %** | 0.0619 | 0.0023 | **0.7 %** | 0.0707 |
| 重新采样（换扩散种子） | 0.0000 | 0 % | 0.0615 | 0.0293 | **8.7 %** | 0.0705 |

同一次运行里的预测标准差（衡量"模型是否塌成常数"）：

| | 全观测 | 置 0 | 灰 | 屏蔽 top | 屏蔽 wrist_L | 屏蔽 wrist_R |
|---|---:|---:|---:|---:|---:|---:|
| **A** | 0.3398 | **0.0000** | **0.0000** | 0.1305 | 0.1626 | 0.1325 |
| **B** | 0.3373 | 0.1332 | 0.1092 | 0.3121 | 0.3011 | 0.2504 |

### 7.1 编码器是健康的

换图移动 37–38%，MAE 恶化 2.2 倍。**视觉通路完全活着**，
这不是 `act_dit` 那种编码器塌缩（`../act_dit/act_dit-encoder-collapse-2026-08.md` §3 的对应数字是 0.0%）。
patch_policy 的前提在这个任务上没有失效。

### 7.2 A 对单相机缺失极度脆弱，B 不脆弱 —— 这是本次两个 head 最大的差异

屏蔽任意一路相机：**A 的 MAE 恶化 3.7–4.2 倍**（0.0615 → 0.23–0.26），
**B 只恶化 1.4–2.0 倍**（0.0707 → 0.097–0.139）。
更说明问题的是预测标准差：A 掉到全观测的 38–48%，B 保持在 74–92%。
而在全黑输入下，**A 的预测标准差是精确的 0.0000——它对每一个样本输出完全相同的动作**，
即彻底塌回一个无条件常数；B 仍保留 0.13 的变化。

机制上说得通：A 的 `PatchACTHead` 只有 **1 层 decoder**（`n_decoder_layers: 1`），
一次 cross-attention 就要从 3 840 个 memory token 读完全部信息，它学到的是一个
**依赖三路 token 联合分布的、脆的**读出方式；B 的 `TransformerForDiffusion` 有 8 层，
且要在 100 步去噪中反复读取同一 memory，天然被迫学出**冗余**表征。

> ⚠️ 屏蔽 = 置零 = 分布外输入。这一栏量的是**"掉一路相机时的鲁棒性"**，
> 不能直接读成"这路相机有多重要"。真正干净的重要性排序只能从 B 读（因为 A 已经饱和到脆性上限）：
> **`wrist_R`（35%）> `wrist_L`（22%）≈ `top`（21%）**。腕部相机比顶视相机重要，
> 与前置报告 §6 的排序一致。

### 7.3 5 帧历史被当成无序集合 —— 最大的一块浪费

**时间倒序只移动 0.7–1.3%。** 把 5 帧观测的时间顺序完全翻转，模型的输出几乎不变。
**冻结历史**（把前 4 帧全部替换成最新帧）也只移动 3.8–4.2%。

两点后果：

1. **模型没有任何速度信息。** 它无法区分"手臂正在向前移动"和"手臂正在向后移动"。
   考虑到 `use_robot_state=False`（§5），模型连位置都要从像素猜，速度更是完全缺席。
2. **`n_obs_steps=5` 是纯粹的算力浪费。** 5 帧 × 3 相机 × 256 patch = 3 840 个 memory token，
   其中 3 072 个（后 4 帧）合计只贡献 ≤4% 的输出变化。
   降到 `n_obs_steps=2` 会把 memory 从 3 840 降到 1 536（−60%），
   编码器前向从 15 次降到 6 次。**按现有测量精度，精度不会掉。**

架构上顺序**是可以被表示的**——`cond_pos_emb` 覆盖全部 `1 + T·P` 个 slot，
块因果掩码也正确地区分了帧——**只是没被学会用。**

### 7.4 扩散采样噪声是 B 独有的精度税

同一观测、只换初始噪声种子，B 的输出移动 **0.0293 rad**（8.7% of σ）；A 是确定性的，移动 0。

对照 §5.1：**部署一个 8 帧 waypoint 覆盖的全部运动只有 0.0386 rad。**
也就是说，**B 每次推理的随机抖动，达到它要发出的运动量的 76%。**
这部分完全是噪声，不携带任何信息，且无法通过 re-anchor 去掉（§5.2 解释了为什么 B 的 re-anchor 收益低）。

## 8. 推理延迟：B 跑不动当前的部署配置

`latency.py`，batch 1，RTX 4090，20 次计时取中位数（前 3 次预热丢弃），单进程独占 GPU。

| | 单次推理 | p10–p90 | 去噪步数 | `n_action_steps` | 自身执行窗口 | 占空比 | **占部署 8 帧窗口（0.267 s）** |
|---|---:|---:|---:|---:|---:|---:|---:|
| **A `act`** | **10.6 ms** | 10.3–11.6 ms | — | 50 | 1.667 s | 0.6 % | **4 %** |
| **B `diffusion`** | **614 ms** | 611–644 ms | **100** | 32 | 1.067 s | 57.6 % | **230 %** |

**B 比 A 慢 58 倍。**

`deploy_config_patch_policy.yaml` 设 `n_action_steps: 8`、`chunk_interval_s: 0.26667`。
**B 的一次推理要 614 ms，是那个窗口的 2.3 倍**——机器人执行完 8 帧后，还要再空等 0.35 s
才能拿到下一个 chunk。按 memory `chunk-interval-s-is-dead-code` 的记录，
实际节奏由服务端 `need_new_chunk` 驱动，所以不会硬性报错，但**开环空档是真实存在的**。

即便按 B 自己的 `n_action_steps=32`（1.067 s），占空比也有 57.6%——**没有任何余量**
留给相机采集、HTTP 往返和轨迹后处理。而 A 在同样的部署窗口下只占 4%。

代价的来源是 `num_train_timesteps: 100` 且 `num_inference_steps: null`（即回落到 100）。
DDPM 100 步全跑。改用 DDIM + 10 步可以把它降到约 60 ms，但那要重新验证精度，
而 §4 已经表明 **B 即使在 100 步下也没有比 A 更准**。

## 9. 建议

按"收益 / 改动成本"排序。前三条是配置单字段，第四条是训练目标。

### 9.1 淘汰 B，保留 A 的 `act` head（立即，零成本）

A 在**每一个** horizon 上都更准（6–8%），推理快 58 倍，显存少 1 GB，训练快 3 小时，
可训练参数少 25%，且输出是确定性的（无 §7.4 的采样抖动）。
B 唯一的优势是单相机缺失时的鲁棒性（§7.2），而这不是当前部署场景的约束
——三路相机都来自同一个 HTTP 响应，要掉一起掉。

**如果仍想保留扩散路线**，最低限度要先做两件事：把 `num_inference_steps` 降到 10–20（DDIM），
以及**在固定 `action_chunk_size` 的前提下重跑一次**，否则 §2 的三字段混淆无法排除。

### 9.2 `n_obs_steps` 5 → 2（立即，单字段，省 60% 算力）

§7.3 实测：后 4 帧合计只值 ≤4% 的输出变化，时间顺序只值 0.7–1.3%。
memory token 3 840 → 1 536，编码器前向 15 次 → 6 次。
reference 的 diffusion preset 本来就是 2。**把省下的算力全部投到 9.3 / 9.4。**

> 注意这条与"想让模型获得速度信息"并不矛盾：现在的 5 帧**没有**提供速度（§7.3），
> 所以砍掉它们不损失任何速度信息。速度要靠 9.3 从 state 的差分里拿。

### 9.3 打开 `use_robot_state`（单字段，精度的主要来源）

`--policy.use_robot_state=true`。§5.2 实测的位姿偏置是 0.0435 rad，
而真实动作离实测位姿只有 0.0152 rad。这一条同时给出精确位姿和（跨 `n_obs_steps` 帧的）精确速度。
A 上 re-anchor 的 **−18.8%** 是这条路收益的一个下界代理。

风险与前置报告 §10.1 一致：state token 只是 1 537 个 memory token 里的**一个**，
加性进入 memory 后被 cross-attention 读取，模型完全可能学不会重视它。
若增益有限，下一步是**加强注入方式**（在每个 patch token 上拼接 state，或走 FiLM/adaLN），
而不是退回 `False`。降到 `n_obs_steps=2`（9.2）会让 state token 的占比从 1/3841 升到 1/1537，
本身就是一个有利因素。

### 9.4 改用相对动作（与 9.3 叠加）

树里已有成熟实现 `lerobot/policies/act_delta/`（`use_relative_actions`、`prepare_relative_stats.py`、
`processor_act_delta.py` 里 "raw → relative → normalize" 的正确顺序）。
让模型预测 `action − state` 而非绝对关节角，**位姿定位问题在结构上消失**。
§5.2 的 re-anchor 实验就是这条路在推理侧的下界估计。

> 与 memory `act-delta-phase2-gate-express` 的区别必须说清：那次相对化在 ACT 上落在不确定区间，
> 但 **ACT 本来就有 state 输入**，相对化只是换参数化。patch_policy 没有 state，
> 相对化解决的是一个它现在根本无法解决的问题，两者不可类比。

### 9.5 不要再调的旋钮（本次已实测无效）

| 旋钮 | 实测依据 |
|---|---|
| 继续加训练步数 | B 从 100 k 到 200 k 只买到 8%，且 @1 非单调（§6） |
| `n_action_steps`（8/16/32/50） | 偏置在第 1 帧就存在（0.0435），与执行帧数无关（§4、§5.2） |
| 提高 `n_obs_steps` | 现有 5 帧里时间顺序只值 0.7–1.3%（§7.3）；应该**降低**而非提高 |
| 单纯换 action head | 值 6–8%，比位姿偏置小一个数量级（§4、§5.2） |

### 9.6 两条流程建议

1. **在 sbatch 里显式写死 `--policy.action_head`（以及所有关心的架构字段）。**
   这次两个 run 的差异**完全来自节点默认值漂移**（§2），不是设计。
   同 memory `act-dit-train-venv-defaults-drift`。
2. **保留中间 checkpoint。** A 的 50 k/100 k/150 k 已被清理，导致 §6 的收敛分析只能对 B 做。

## 10. 这份报告的边界

- **全部是离线开环指标，没有真机成功率。** 也没有重建部署侧的 Hermite 桥接
  （`send_next_action_chunk` 会把前 14 个关节改写成三次曲线，见 memory `record-chunk-is-filtered`
  和前置报告 §8）。§4 量的是**模型发出的 chunk**，不是机器人执行的轨迹。
  §4.1 关于夹爪优于 `hold_state` 的结论，因此**不能**直接推翻前置报告 §8 的相反结论——
  那里量的是桥接后的轨迹，且用的是更远的 held-out 分布。
- **三字段混淆（§2）没有解开。** "A 比 B 好 7%"无法在 head / chunk 长度之间归因。
- **评测集离训练分布近。** §3.2 已说明：同一 checkpoint 在 `batch_1–4` 上的位姿偏置是这里的 1.5 倍。
  本报告的绝对数字是乐观值，**相对排序**（A > B、时间顺序无用、B 慢 58 倍）不受影响。
- **屏蔽相机是分布外输入**，§7.2 量的是鲁棒性而非相机重要性，已在正文标注。
- **没有测**：部署相机的真实 FOV / 分辨率是否与训练一致；`num_inference_steps` 降档后 B 的精度；
  `use_robot_state=true` 的实际增益（§9.3 只有代理证据）。
